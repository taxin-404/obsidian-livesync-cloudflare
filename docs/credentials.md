# Credentials, secrets and variables

Everything a deployment needs to authenticate: what is chosen by you, what is
generated for you, what ships with the code, and how to make each one.

The short version: **exactly one value is required and chosen by you
(`COUCHDB_PASSWORD`); two more (`SETUP_URI`, `SETUP_URI_PASSPHRASE`) are
generated from a vault when you want a scannable setup page; everything else is
in `wrangler.jsonc` and deployed for you.** Nothing is ever generated by the
deploy itself.

## The three kinds of value

| Kind | Examples | Who creates it | Where it lives |
| --- | --- | --- | --- |
| Chosen by you | `COUCHDB_PASSWORD`, optional `PAGE_PASSWORD` | you, once | Worker secret |
| Generated from a vault | `SETUP_URI`, `SETUP_URI_PASSPHRASE` | a script or the plugin | Worker secret |
| Shipped with the code | `COUCHDB_USERNAME`, `CORS_ORIGINS`, `BACKUP_*`, bindings | `wrangler.jsonc` / the deploy | the repository |

A deploy copies the third row and leaves the first two alone. That is why
pushing new code can never invalidate a paired device.

## Worker secrets

| Name | Required | Created by | Used for | If it is absent |
| --- | --- | --- | --- | --- |
| `COUCHDB_PASSWORD` | **yes** | you, a password generator, or `npm run rotate:password` | HTTP basic auth for every request from Obsidian | declared in `secrets.required`, so Wrangler reports it as missing; the Worker answers `503` instead of serving the vault |
| `PAGE_PASSWORD` | no | you, but do not set it — rotation cannot keep it in sync | overrides the password that opens the connection-details page | the page falls back to `COUCHDB_PASSWORD` |
| `SETUP_URI` | no | `scripts/generate-setup-uri.sh`, the plugin, or `npm run rotate:password` | makes the page show a setup URI (and QR code) instead of raw connection fields | the page shows URL, database, username and password instead |
| `SETUP_URI_PASSPHRASE` | no | generated together with the URI | unlocks `SETUP_URI` for the device being onboarded | together with a missing URI, the page falls back to raw fields |

`COUCHDB_USERNAME` is **not** a secret — it is `admin`, in `wrangler.jsonc`.

### Rules for these values

- **`PAGE_PASSWORD` must stay unset for rotation.** The Worker supports a
  separate gate password, but `rotate:password` does not rewrite it: a matching
  value fails after the password changes, and a different value fails before
  anything is pushed. Either way the page would demand a value the tool cannot
  keep in sync. With it unset, the page uses `COUCHDB_PASSWORD`.
- **The setup URI and its passphrase must come from the same source.** Mismatched
  halves produce a page whose URI cannot be decrypted.
- **The setup URI embeds the password.** A URI generated for `A` will not pair a
  device with a server whose password is `B`. Generate the URI *after* choosing
  the password, or let one command do both.
- **Both setup secrets are capped at 5.1 kB per Worker secret.** `rotate:password`
  refuses anything over 4800 bytes, and builds a compact profile for that reason.
  A "full settings" URI from the plugin can exceed the cap; if Wrangler rejects
  it, use `npm run rotate:password` instead.

## Values that ship with the code

These are in `wrangler.jsonc` and re-applied on every deploy. **Do not add them in
the dashboard**: a deploy overwrites them with the file's values, and because
`keep_vars` is not set, dashboard-only *variables* on this Worker are removed.

| Name | Value | Purpose |
| --- | --- | --- |
| `COUCHDB_USERNAME` | `admin` | basic-auth user |
| `CORS_ORIGINS` | `app://obsidian.md,capacitor://localhost,http://localhost` | browser origins allowed to call the Worker |
| `BACKUP_ENABLED` | `"true"` | scheduled R2 backups |
| `BACKUP_DATABASE` | `vault` | database being backed up |
| `BACKUP_DAILY` / `BACKUP_WEEKLY` / `BACKUP_MONTHLY` | `30` / `8` / `24` | history retained |

Created by the deploy, not entered by hand:

| Name | Kind | Notes |
| --- | --- | --- |
| `POUCH_DATABASES` | Durable Object binding | class `PouchDatabase`, migration tag `v1` |
| `BACKUP_BUCKET` | R2 binding | bucket `obsidian-sync-backups` |
| `BACKUP_BUCKET` (`dev`) | R2 binding | `dev` environment only |
| — | migration `v1` | `new_sqlite_classes`; deleting or renaming the tag strands existing data |

The distinction matters: **secrets survive a deploy, variables do not.** Editing
a variable in the dashboard is temporary; editing a secret there is permanent.

## Local files

`.setup-uri`, `.dev.vars` and the password file are gitignored or outside the
repository; `data.json` lives inside your vault and should never be committed.
Modes are `600` where the tooling writes them.

| Path | Written by | Contents | If it is lost |
| --- | --- | --- | --- |
| `~/.config/obsidian-livesync/server-password` | `rotate:password`, or by hand | the current `COUCHDB_PASSWORD`, plaintext | regenerate with `--rebuild`, or re-pair manually |
| `.setup-uri` (repository root) | `scripts/generate-setup-uri.sh` | `vault_passphrase`, `uri_passphrase`, `id_recovery_code`, `uri` | re-run the script only for a *new* deployment; for an existing vault use the plugin's **Copy Setup URI** or the connection page |
| `<vault>/.obsidian/plugins/obsidian-livesync/data.json` | the plugin, or `rotate:password` | the remote configuration with the password encrypted inside an envelope | re-pair the device |
| `.dev.vars` | you, `cp .dev.vars.example .dev.vars` | `COUCHDB_PASSWORD` for local deploy and `wrangler dev` | recreate it |

Override the password file with `LIVESYNC_PASSWORD_FILE` or `--password-file`.

`.setup-uri` is **not** rewritten by `rotate:password`. After a rotation, a fresh
URI comes from the connection page or from **Copy Setup URI** on a paired device.

Keep the vault E2EE passphrase (in `.setup-uri` for a fresh deployment) in a
password manager. It is not recoverable, and without it the server data and the
R2 backups are unreadable by design.

## How to make each secret

### `COUCHDB_PASSWORD` — choose one

Any long random string works. It travels in an HTTP basic-auth header, so keep it
to URL-safe characters (letters, digits, `-`, `_`); no quotes or spaces.

```sh
openssl rand -hex 16
printf '%s' '<the-value>' | npx wrangler secret put COUCHDB_PASSWORD --name obsidian-sync
npx wrangler secret list --name obsidian-sync   # names only; values cannot be read back
```

For a local deploy, put it in `.dev.vars` instead and run
`npm run deploy -- --secrets-file .dev.vars`.

For a deployment that is **already paired with Obsidian**, do not use the two
commands above on their own: use
[`npm run rotate:password`](#the-rule-that-prevents-every-lockout), which moves
the password, both setup secrets and the local vault together.

### `SETUP_URI` + `SETUP_URI_PASSPHRASE` — generate, then publish

**Fresh deployment, no vault yet.** The script invents a vault E2EE passphrase if
you do not supply one, generates the URI, and writes `.setup-uri`. It needs
[Deno](https://deno.com) and a password (from `LIVESYNC_PASS` or `.dev.vars`):

```sh
LIVESYNC_HOST='https://<worker>.<subdomain>.workers.dev' \
LIVESYNC_PASS='<the same COUCHDB_PASSWORD>' \
npm run setup:uri
```

The password must be **the same one** you added as the Worker secret: it is
embedded in the URI. Without `LIVESYNC_PASS` the script reads
`COUCHDB_PASSWORD` from `.dev.vars`, and stops if neither is present.

Publish the result so the connection page becomes a QR code. Use the same
password the URI was generated with — it is embedded in the URI:

```sh
sed -n 's/^uri=//p' .setup-uri | npx wrangler secret put SETUP_URI --name obsidian-sync
sed -n 's/^uri_passphrase=//p' .setup-uri | npx wrangler secret put SETUP_URI_PASSPHRASE --name obsidian-sync
```

`--name` is the Worker name from `wrangler.jsonc` (`obsidian-sync`); substitute
yours if you renamed it. Wrangler needs `npx wrangler login` once.

Then pair the first device from the page (or from `.setup-uri`) using
[Connect Obsidian](../README.md#connect-obsidian-first-device).

**Existing vault with notes in it.** Do not run the script: it creates a *new*
vault passphrase, which cannot read the existing notes. Instead:

- on a paired device, **LiveSync → Copy Setup URI** and publish those two values
  with the commands above, or
- run `npm run rotate:password`, which regenerates all three values and updates
  the local vault in one verified step.

### `PAGE_PASSWORD` — leave it unset

The Worker does support a separate password for the connection page
(`PAGE_PASSWORD` overrides `COUCHDB_PASSWORD`), but the rotation tooling never
rewrites it. If it equals the current password, rotation passes the preflight
and then fails verification once the password changes; if it differs, rotation
fails immediately. Either way the run rolls back.

Leave it unset. If one is already set, delete it before rotating:

```sh
npx wrangler secret delete PAGE_PASSWORD --name obsidian-sync
```

## What a deploy does and does not touch

| Item | On every deploy |
| --- | --- |
| Worker code | replaced |
| `wrangler.jsonc` variables | replaced |
| Dashboard-only variables | **removed** (`keep_vars` is not set) |
| Worker secrets | untouched — never read, never deleted |
| Durable Object data | untouched; migrations run by tag |
| R2 backups | untouched |

So a redeploy, a rollback, or a Workers Builds push cannot break pairing. The
only way to damage a working setup by deploying is to edit a **secret** in the
dashboard.

## The rule that prevents every lockout

Five things must agree, and rotation has **no grace period**: every paired device
must re-pair afterwards.

1. `COUCHDB_PASSWORD` (Worker secret)
2. `SETUP_URI` (Worker secret)
3. `SETUP_URI_PASSPHRASE` (Worker secret)
4. `~/.config/obsidian-livesync/server-password` (local)
5. the encrypted remote configuration inside the vault's `data.json`

Never change one of them alone. Two commands move all five:

```sh
npm run rotate:password -- --vault ~/Documents/notes
npm run check:secrets  -- --vault ~/Documents/notes
```

Quit Obsidian first: the plugin rewrites `data.json` from memory on exit, so the
tool refuses to run against a live vault (override only with `--force`).

`check:secrets` prints five links and is the fastest way to know whether a
deployment is healthy:

```
server password           ok
setup page gate           ok
setup URI password        ok
setup URI device profile  ok
vault connection          ok
```

### Rotation order (why it does not lock you out)

1. stage the new local files — nothing is renamed yet;
2. push and verify `SETUP_URI` and `SETUP_URI_PASSPHRASE`, checking the page
   still opens with the **old** password;
3. push and verify `COUCHDB_PASSWORD`: new password → `200`, old password → `401`,
   page still serves the new URI whose embedded password matches;
4. only then rename the staged files into place.

If a push fails, the secrets already replaced are re-pushed with their old values
and no local file is touched. If the saved password is genuinely lost, use
`--rebuild`: it builds a compact profile from the vault's encryption settings and
replaces all three secrets, without pretending to roll back.

## Recovery

| Symptom | Cause | Fix |
| --- | --- | --- |
| Page accepts no password; `/vault` returns `401` for old and new | a secret was changed on its own | `npm run rotate:password -- --vault <path> --rebuild` |
| Page shows URL, database, username, password instead of a URI | `SETUP_URI` or its passphrase is not bound | generate and publish both, or delete both to keep the fallback |
| Page shows a URI but the passphrase is rejected | the two halves came from different runs | re-publish both from the same source |
| Phone gets `401`, desktop is fine | the phone still holds an older password | re-pair from a fresh QR code |
| `wrangler secret put` rejects the URI as too large | full-settings URI over 5.1 kB | use `npm run rotate:password` (compact profile, 4800-byte guard) |
| `.setup-uri` no longer pairs | it predates a rotation | take a fresh URI from the page or **Copy Setup URI** |
| Vault E2EE passphrase lost | — | the data is unrecoverable; this is the design |

## Fastest paths

**Fresh deployment → first synced note (minimum path, one secret).**

1. Deploy ([README](../README.md#deploy)).
2. Add `COUCHDB_PASSWORD` as a Secret.
3. Back up the vault; install LiveSync; disable Obsidian Sync/iCloud for it.
4. `LIVESYNC_HOST='https://<worker>...' LIVESYNC_PASS='<same password>' npm run setup:uri`
5. Obsidian → LiveSync → **Rerun Onboarding Wizard** → *first time* → *Use a Setup
   URI* → paste → passphrase → **Test Settings and Continue**.
6. **Restart and Initialise Server** → **Enable LiveSync**.

Once the two setup secrets are published, step 4 disappears and steps 5–6 become
"open the page and scan the QR code" on the phone.

**Add another device (2 steps).** On a paired device: `Ctrl+P` → **Show settings
as a QR code**. On the new device: LiveSync → *Rerun onboarding* → *Add another
device* → scan → *"Compare time and take newer"* — never "Overwrite all with
remote files".

**Rotate (3 steps).** Quit Obsidian → `npm run rotate:password -- --vault <path>`
→ re-pair every device. Verify with `npm run check:secrets -- --vault <path>`.
